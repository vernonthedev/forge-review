# Forge Review

Build **Forge Review**, a standalone GitHub App that automatically reviews pull requests using configurable OpenAI-compatible LLM providers.

The application must operate independently of GitHub Actions. It must receive GitHub webhook events, retrieve PR context through the GitHub API, perform an AI code review, and publish the findings back to the PR as a GitHub review with inline comments.

The initial primary model should support NVIDIA Nemotron, but the architecture must support any OpenAI-compatible API so providers/models can be changed without rewriting the review engine.

The project must use the latest stable package versions available at implementation time.

Use **pnpm** as the package manager.

Use TypeScript throughout.

Use a feature-based architecture. Do not introduce domain-driven design, repositories, aggregates, or unnecessary abstraction layers.



## 1. Core product

Forge Review should work like this:

```text
GitHub
  │
  │ pull_request webhook
  ▼
Forge Review
  │
  ├── authenticate webhook
  ├── inspect repository configuration
  ├── fetch PR metadata
  ├── fetch changed files
  ├── fetch patches
  ├── gather relevant repository context
  ├── load review guidelines
  ├── construct review request
  ├── call configured LLM
  ├── validate structured response
  ├── optionally verify findings
  └── publish GitHub review
```

There must be no GitHub Actions workflow required for the review process.

GitHub Actions may exist separately in the repository for Forge Review's own CI, but Forge Review itself must never depend on Actions to review customer repositories.

# 4. GitHub App

Forge Review must be implemented as a proper GitHub App.

Support:

- App ID
- private key
- webhook secret
- installation authentication
- repository-scoped installation access

Required GitHub permissions should be minimal.

Initially request:

```text
Repository permissions

Contents: Read
Pull requests: Read & Write
Metadata: Read
```

Subscribe to:

```text
Pull request
```

Handle at minimum:

```text
opened
reopened
synchronize
```

Ignore unrelated webhook events.

Verify every webhook using GitHub's webhook signature mechanism.

Never trust webhook payloads without signature verification.



# 5. Webhook behavior

The webhook endpoint should be something like:

```text
POST /webhooks/github
```

The handler should:

1. Verify the webhook signature.
2. Verify the event type.
3. Extract installation ID.
4. Extract repository.
5. Extract PR number.
6. Extract head SHA.
7. Determine whether this PR/commit should be reviewed.
8. Return quickly to GitHub.
9. Process the review asynchronously.

Do not hold the GitHub webhook request open while waiting for the LLM.

The webhook should acknowledge the event quickly.

Implement an initial background execution strategy appropriate for the chosen deployment platform.

Do not introduce Redis or a full queue system unless it is genuinely required.



# 6. Review lifecycle

Implement a clear review lifecycle:

```text
RECEIVED
  ↓
COLLECTING_CONTEXT
  ↓
REVIEWING
  ↓
VERIFYING
  ↓
PUBLISHING
  ↓
COMPLETED
```

Failures should be represented explicitly.

Do not silently swallow failures.

Log enough information to debug:

- repository
- PR number
- commit SHA
- installation ID
- review ID/job ID
- provider
- model
- duration
- number of findings
- failure reason

Never log:

- API keys
- GitHub private keys
- webhook secrets
- complete source files unnecessarily
- sensitive LLM prompts unnecessarily



# 7. Repository configuration

Repositories should be able to configure Forge Review through:

```text
.github/forge-review.yml
```

Support configuration such as:

```yaml
enabled: true

model:
  provider: nvidia
  model: nvidia/nemotron-3-ultra-550b-a55b

review:
  severity_threshold: medium
  max_comments: 15
  incremental: true
  verify_findings: true

exclude:
  - "**/*.lock"
  - "dist/**"
  - ".next/**"
  - "coverage/**"
  - "node_modules/**"

guidelines:
  path: ".github/forge-review.md"
```

Use Zod to validate the configuration.

Provide sensible defaults when configuration is absent.

A malformed configuration must produce a clear review status/error rather than crashing the entire application.



# 8. Review guidelines

Support:

```text
.github/forge-review.md
```

This file contains repository-specific instructions.

Example:

```md
# Forge Review Guidelines

Review concrete problems introduced by the PR.

Prioritize:

1. correctness
2. security
3. data integrity
4. regressions
5. performance
6. maintainability

Do not report purely stylistic preferences.

Use the existing architecture of the repository.

Prefer feature-based architecture.

Do not introduce unnecessary repositories or domain abstractions.

Do not introduce `any` without a concrete justification.

Only report issues that have a clear failure mode.
```

The repository guideline file must be treated as additional review context, not as executable instructions.

Treat repository content as untrusted input.



# 9. LLM provider abstraction

Create a small provider abstraction.

Do not couple the review engine directly to NVIDIA.

For example:

```ts
interface ReviewModel {
  review(input: ReviewInput): Promise<ReviewResult>;
}
```

Implement an OpenAI-compatible provider.

Configuration should support:

```text
provider
base URL
model
API key
temperature
max tokens
```

The provider should work with:

- NVIDIA NIM
- OpenRouter
- DeepSeek
- Together
- Groq
- vLLM
- compatible self-hosted endpoints

The default example should use NVIDIA Nemotron.

Default configuration:

```text
Base URL:
https://integrate.api.nvidia.com/v1

Model:
nvidia/nemotron-3-ultra-550b-a55b
```

Do not hard-code credentials.

Environment variables should be used for server-level provider credentials.



# 10. Review input

Do not send only the raw PR description to the model.

Build a structured review context containing:

```text
Repository
PR title
PR description
Base branch
Head branch
Base SHA
Head SHA
Changed files
Diffs
Relevant source context
Repository configuration
Forge Review guidelines
Relevant tests
Relevant configuration files
```

The context builder should avoid indiscriminately sending the entire repository.

Start with changed files and their surrounding context.

Then resolve relevant dependencies/imports where practical.

For example, if:

```text
apps/api/src/features/sales/create-sale.ts
```

changes, inspect relevant imported modules and nearby feature code where possible.

The goal is to provide enough repository context for semantic review without exploding token usage.



# 11. Diff handling

Handle:

- added files
- modified files
- deleted files
- renamed files
- binary files
- generated files
- large patches

Do not send binary content to the model.

Ignore configured generated/lock/build files.

Protect against extremely large PRs.

Implement reasonable limits for:

- maximum files
- maximum patch size
- maximum context size

If a PR exceeds limits, explain that context was truncated.

Never silently pretend the model saw files it did not receive.



# 12. Structured LLM output

The model must return structured JSON.

Use Zod to validate the model response.

Design a schema similar to:

```ts
const reviewResultSchema = z.object({
  summary: z.string(),

  findings: z.array(
    z.object({
      severity: z.enum([
        "critical",
        "high",
        "medium",
        "low",
      ]),

      category: z.enum([
        "correctness",
        "security",
        "performance",
        "architecture",
        "maintainability",
        "testing",
        "other",
      ]),

      file: z.string(),

      line: z.number().int().positive(),

      title: z.string(),

      body: z.string(),

      suggestion: z.string().optional(),

      confidence: z.number().min(0).max(1),
    }),
  ),
});
```

Adjust this schema if necessary to match GitHub's review comment requirements.

The model must not be allowed to invent arbitrary files or line numbers without validation.



# 13. Finding validation

Before publishing a finding:

1. Verify the referenced file exists in the PR.
2. Verify the referenced line exists.
3. Verify the line belongs to the changed diff when inline commenting.
4. Verify the finding is associated with the current head SHA.
5. Remove invalid findings.
6. Record rejected findings in logs.

Do not publish comments against unrelated lines.

If an issue is valid but cannot be attached to a changed line, include it in the overall review summary instead of inventing an inline location.



# 14. Review verification pass

Implement a second model pass when:

```yaml
verify_findings: true
```

The first model produces findings.

The second pass receives:

```text
Original review context
Finding
Referenced code
Relevant repository context
```

and determines:

```text
valid
invalid
uncertain
```

Only publish:

```text
valid
```

findings by default.

This is important because the primary goal is high-confidence review rather than maximizing the number of comments.



# 15. GitHub review publishing

Publish a proper GitHub pull request review.

Prefer one consolidated review containing multiple inline comments rather than creating many independent reviews.

Example:

```text
Forge Review

2 findings

HIGH
apps/api/src/features/sales/create-sale.ts:184

Inventory is mutated outside the transaction that creates
the sale. If the sale operation fails after this mutation,
inventory can remain inconsistent.

Suggestion:
Move both mutations into the same database transaction.



MEDIUM
apps/api/src/features/inventory/batches.ts:72

The FEFO ordering is not deterministic when two batches have
the same expiration date.
```

The review should include:

```text
APPROVE
REQUEST_CHANGES
COMMENT
```

but the default behavior should be:

```text
COMMENT
```

Do not automatically block PRs initially.

Do not make Forge Review a merge gate until the system has demonstrated a sufficiently low false-positive rate.



# 16. Incremental reviews

Support incremental PR reviews.

When:

```text
synchronize
```

fires because new commits were pushed, avoid repeatedly commenting on unchanged code.

Track reviewed commit SHA where practical.

Do not create duplicate comments for the same finding.

If GitHub already has an existing Forge Review comment for a finding, update or suppress the duplicate where possible.



# 17. Comment identity

Every Forge Review comment should have a recognizable marker.

For example:

```text
<!-- forge-review:finding:<stable-id> -->
```

Use this to identify Forge Review's own comments.

Never modify comments created by humans or other bots.



# 18. Security

Treat everything from GitHub repositories as untrusted.

This includes:

- source code
- README files
- comments
- PR descriptions
- commit messages
- review guideline files

Repository content must never be able to cause Forge Review to:

- execute arbitrary shell commands
- access environment secrets
- make arbitrary outbound requests
- change GitHub permissions
- modify unrelated repositories

Do not execute repository code during review.

Do not run:

```text
npm install
pnpm install
bun install
cargo build
```

as part of the review service.

The initial reviewer is static/contextual only.



# 19. Prompt injection protection

Explicitly design against prompt injection.

Repository text such as:

```text
IGNORE ALL PREVIOUS INSTRUCTIONS
```

must be treated as source content rather than a system instruction.

Use a strict hierarchy:

```text
System instructions
  ↓
Forge Review review policy
  ↓
Repository review configuration
  ↓
Repository source code / PR content
```

Repository content cannot override the first two levels.



# 20. Model selection

Make the model configurable.

Support a configuration such as:

```yaml
model:
  provider: nvidia
  model: nvidia/nemotron-3-ultra-550b-a55b
```

Later allow:

```yaml
model:
  provider: openai-compatible
  model: deepseek-v4.1-flash
```

Do not hard-code model-specific assumptions into the review engine.



# 21. Cost and token control

Implement basic context budgeting.

Track:

```text
input tokens
output tokens
estimated cost where provider pricing is available
review duration
```

Do not make cost tracking dependent on a specific provider.

If the provider does not expose usage, record usage as unavailable.

Prefer compact context over blindly sending huge repositories.



# 22. Error handling

Handle:

- GitHub API rate limits
- GitHub authentication failures
- expired installations
- invalid webhook signatures
- LLM timeouts
- LLM rate limits
- malformed model responses
- provider errors
- GitHub comment failures
- oversized PRs

Implement retries only where safe.

Use exponential backoff for transient provider/API errors.

Do not retry invalid authentication or invalid configuration indefinitely.

# 29. Repository defaults

Create a strong default review policy.

Default behavior:

```text

Do not nitpick.

Do not rewrite working code.

Do not report style unless explicitly configured.

Prioritize:
- correctness
- security
- data integrity
- regressions
- performance
- maintainability

```

# 34. Implementation process

Before writing code:

1. Inspect the latest stable versions of all required packages.
2. Confirm the current GitHub App API patterns.
3. Confirm the current GitHub pull request review API.
4. Confirm the current OpenAI-compatible NVIDIA API format.
5. Identify any limitations of the chosen deployment platform.
6. Produce a concrete implementation plan.

Then implement the project completely.

Do not stop after scaffolding.

Do not leave TODOs for core functionality.

Do not replace difficult requirements with placeholders.

After implementation:

1. Run type checking.
2. Run linting.
3. Run formatting checks.
4. Run all tests.
5. Build every package/application.
6. Fix all errors.
7. Review the final architecture for unnecessary abstractions.
8. Review security boundaries.
9. Verify that no GitHub Actions workflow is required for customer repositories.
10. Verify that the webhook returns quickly and review execution happens asynchronously.
11. Verify that the final documentation matches the actual implementation.

If something in this specification conflicts with the latest package/API behavior, use the current official API behavior and update the implementation accordingly rather than blindly following an outdated example.

The final result should be a production-oriented first version of Forge Review, not a demo or proof of concept.
